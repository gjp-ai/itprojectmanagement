# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-file demo/training web app: a Kanban board for UOB's internal IT PMO. The entire app — markup, styles, and logic — lives in `index.html`. There is no build step, no package manager, and no server.

## Running / testing

Open `index.html` directly in a browser (double-click, or `open index.html`). There is no dev server, bundler, or test suite — verify changes by loading the file and exercising the UI manually (or via a headless browser tool if available).

## Hard constraints (do not violate these)

- **Vanilla only**: plain HTML/CSS/JS. No frameworks (React, Vue, jQuery, Tailwind, etc.), no build tooling, no npm packages.
- **Single file**: all markup, one `<style>` block, and one `<script>` block stay in `index.html`. It must keep working via double-click with no server.
- **No external resources**: no CDN scripts, no Google Fonts, no image files. Use the system font stack and inline SVG/Unicode glyphs for icons.
- **No persistence**: board state lives only in the in-memory `state` object in the `<script>` block. Do not add `localStorage`, `sessionStorage`, `IndexedDB`, or cookies — a page refresh is supposed to reset the board to the seeded demo data.
- **No real UOB branding**: this is an internal demo, not an official system. Keep the neutral "UOB IT PMO" text wordmark and corporate-blue palette only — no real logos/trademarks.
- **Escape all user-supplied strings** before inserting into HTML via the `escapeHtml()` helper. Never use raw `innerHTML` with unsanitised input.

## Architecture

Everything is organized around one source of truth:

```js
state = { tasks: [...], filters: {...}, nextIdCounter: N }
```

All UI is a pure function of `state`; nothing else mutates the DOM directly. The render/mutate flow is:

1. A mutation function (`addTask`, `moveTask`, `deleteTask`) updates `state.tasks`.
2. `renderBoard()` rebuilds the board HTML from `state` (via `getFilteredTasks()` → `renderCard()` per task) and calls `renderSummary()` and `wireBoardEvents()`.
3. `wireBoardEvents()` re-attaches drag/drop, move-select, and delete-button listeners after every re-render, since `renderBoard()` replaces the board's `innerHTML` wholesale.

Key functions and their roles (all in the `<script>` block of `index.html`):

- `escapeHtml`, `formatDate`, `isOverdue`, `priorityClass`, `generateTaskId` — small pure helpers.
- `applyFilters` / `getFilteredTasks` — client-side filtering over `state.tasks` by project, assignee (substring), and priority.
- `renderBoard` / `renderCard` / `renderSummary` — the only place DOM content is generated; re-render from state rather than patching the DOM piecemeal.
- `addTask` / `moveTask` / `deleteTask` — the only functions that mutate `state.tasks`.
- `pendingDeleteIds` (a `Set`, not part of `state`) tracks which cards are showing the inline "Delete? Yes / No" confirmation — this is deliberately kept out of the task data model.
- `notifyNewTask` — fires the FormSubmit AJAX call for a new task. Wrapped in try/catch; a failure here must never break the board (it only surfaces a warning toast).
- `showToast` — transient toast notifications (success/warning/error), rendered into the `aria-live="polite"` toast region.
- `openModal` / `closeModal`, `validateForm` / `displayFieldErrors` — Add Task modal lifecycle and inline (non-`alert()`) validation.
- `wireBoardEvents` vs `wireStaticEvents` — the former re-binds per-card/per-column listeners after every board re-render; the latter binds once at startup (filters, modal open/close, form submit).

### FormSubmit integration

`FORMSUBMIT_ENDPOINT` at the top of the `<script>` block is the single place to change the notification email address. FormSubmit requires a one-time activation: the first submission to a given address triggers a confirmation email, and no notifications deliver until that link is clicked — this has no effect on board functionality since the card is added optimistically before the network call.

### Kanban semantics

- Four fixed columns/statuses: `Backlog`, `In Progress`, `Blocked`, `Done` (defined in the `COLUMNS` array — do not reorder without updating seed data expectations).
- Priority (`Critical`/`High`/`Medium`/`Low`) drives left-border color and pill color via the `priority-*` CSS classes generated by `priorityClass()`.
- Drag-and-drop uses the native HTML5 DnD API; the `Move ▸` `<select>` on each card is the required keyboard-accessible equivalent — both call the same `moveTask()`.
- "Overdue" is derived, not stored: `isOverdue()` checks `dueDate < today && status !== "Done"`.
